# Compiler naming audit

Names currently mix languages, algorithms, host shapes and runtime structures.
The useful distinction is the implemented boundary, not a claim that one crate is
“planning” and another is “execution.” This audit proposes names only and
implements no API, crate-name or semantic changes.

The inventory comes from the [workspace manifest](../Cargo.toml),
[frontend exports](../crates/mini-linq/src/lib.rs) and
[feature declarations](../crates/mini-linq/Cargo.toml). It covers all **44 exported
procedural macros**, including exports generated by `native_entry!`.

## Crate responsibilities and candidate names

| Current crate | Actual responsibility | Naming recommendation |
| --- | --- | --- |
| [cq-ir](../crates/cq-ir/src/lib.rs) | Syntax, validity and structural facts for CQ, RA, IX, Access, Pipeline and Native | Keep; it owns languages, not lowering policies. |
| [cq-plan](../crates/cq-plan/src/lib.rs) | CQ → RA, including legal scheduling, YA and derivations | `cq-query-lowering`; `cq-planning` still hides lowering, and `optimizer` would falsely suggest an RA → RA pass. |
| [cq-index](../crates/cq-index/src/lib.rs) | RA → IX under base, result or empty demand policies | `cq-index-policy`; `cq-index-analysis` understates the policy choice and suggests facts rather than selected requests. |
| [cq-realize](../crates/cq-realize/src/lib.rs) | RA or IX → Rust containing Access/Native, including layouts, lifetimes and Rust hosts | `cq-relation-lowering`; “realize” alone identifies neither source nor action. |
| [cq-native](../crates/cq-native/src/lib.rs) | Native operation → Rust or further selected Native/Access invocations | `cq-native-lowering`; it emits operations and contains no runtime provider objects. |
| [cq-execution](../crates/cq-execution/src/lib.rs) | Access → Pipeline, or Access → eager Rust | `cq-access-lowering`; the crate runs during compilation, not query execution. |
| [cq-pipeline](../crates/cq-pipeline/src/lib.rs) | Pipeline → Rust with distinct/support/set/existential observations | `cq-pipeline-lowering`; consistent with the other lowering crates. `codegen` is accurate but does not justify a different naming convention. |
| [cq-compose](../crates/cq-compose/src/lib.rs) | Typed recipes and dispatch over existing compiler functions | Keep; it is composition, not another IR or lowering stage. |
| [cq-storage](../crates/cq-storage/src/lib.rs) | Runtime structures, operation traits and counters | Keep; blocks, selections, summaries and replay are data structures. `cq-runtime` would obscure their deliberately limited scope. |
| [mini-linq](../crates/mini-linq/src/lib.rs) | Proc-macro parsing, dispatch, continuation paths and public entries | Keep the product API name; describe it as the macro frontend, not as a single compiler pass. |

`mini-linq-course` is the teaching/example root; [cq-workloads](../workloads/Cargo.toml)
is the query/data catalog. [cq-xtask](../xtask/Cargo.toml) is a separate tooling
workspace for generation, explanation and differential checks. None is an IR stage.

## Module and function names

| Current implementation names | Assessment / candidate |
| --- | --- |
| `cq-plan::{canonical,prefix,graph}` | These are CQ-lowering alternatives. `written_order`, `clause_prefix`, `hypergraph` describe them more directly; `graph` includes YA plus fallback scheduling, not just graph construction. |
| `graph::{strategy,rules,ya,hypergraph,check}` | Useful distinctions: policy selection, rule application, reduction, structure and verification. Keep these responsibilities visible. |
| `cq-index::{input,result,none}` | `base_demands`, `result_demands`, `no_demands` distinguish requests from allocated indexes. |
| `cq-realize::{hash_inputs,hash_prefix,hash_materialized}` | `base_hash`, `prefix_hash`, `materialized_hash` distinguish index namespace/domain and materialization. Their existing `compile_input_indexed`/`compile_lazy_indexed` terminology should migrate with the modules. |
| `cq-realize::{relations,borrowed_scans}` | `configured` and `borrowed_nested` better distinguish selected providers from the borrowed nested-scan implementation. Neither name implies a generic optimizer. |
| `cq-native::{rows,candidates,keys,witnesses,pairs}` | The groups identify operation domains. `rows::replay` is only Build/Scan, so it must not be documented as implementing the full row-set protocol. `rows::native` could be `set_ops` to name its shared emitter. |
| `cq-execution::{pull,push}` | `to_pipeline`, `to_set_loops` name actual lowerings. Retain pull/push terminology in explanations, not as evidence of symmetric output IRs. |
| `cq-pipeline::{iterator,collect,stream,exists}` | `distinct_iter`, `collect_set`, `support_iter`, `exists` expose observation contracts. `operators` remains their shared Rust adapter emitter. |

Within a named implementation, prefer `compile`, `check_domain` and `check` for
lowering, admission and correspondence. Use `compile_program`/`compile_callable`
only where Rust host shape really differs; a callable host is not another IR.

## Caller-bound names are a separate naming problem

[Generated frontend paths](../crates/mini-linq/src/lib.rs),
[input bindings](../crates/mini-linq/src/entry.rs) and
[Native configuration](../crates/mini-linq/src/native_input.rs) are the evidence.

| Current binding / configuration | Actual role and naming implication |
| --- | --- |
| `mini_linq`, caller-authored `mini_linq::query` | The first can alias a facade module. `query` is an example's import alias, **not an exported macro**. It need not share the chosen implementation's name. |
| `canonical_query`, `prefix_query`, `graph_query`; `choose_indexes`, `choose_realization`; `input_indexes`, `result_indexes`, `hash_*` | Generated caller-relative continuation paths. Some name an algorithm, others a dispatcher. Every resolved path is replaceable only within its input/output contract. |
| `pull`, `pull_set`, `pull_stream`, `pull_exists`; the four `*_pipeline` paths | API slots currently contain implementation names. Neutral role aliases such as `access_distinct`, `access_set`, `access_support`, `access_exists` would avoid implying that the selected implementation must be pull. Such a change requires migrating emitters and every facade. |
| `inputs::R`, `replay_rows`, `storage` | Per-input Native implementation, replay Native implementation and Rust storage path. These are three different kinds of binding; only the first two are macros. |
| Explicit `access`, `iterator`, provider and algorithm paths | Caller-selected continuations, not universal fixed aliases. Native `iterator` actually accepts an Access macro; `access_support` would describe replay's requirement more precisely. |

The [configured relation directives](../crates/mini-linq/src/relation_input.rs)
also overload names: `materialize/results` select row providers, `join/joins`
select Pairs algorithms, and `scan/scans` select Candidates implementations.
`result_rows`, `pairs` and `candidates` would name those roles more accurately.
Its `storage` directive supplies observed-counter storage; Native `storage`
supplies operation data structures. Those contexts should not imply one shared API.

## Boundary issues that renaming cannot resolve

- Configured lowering accepts **RA**, while hash and borrowed lowerings accept
  **IX**. They are not interchangeable implementations of one identical input API.
- Pull emits **Pipeline**; push emits **Rust**. They can satisfy the same set
  observation at a composed Access hole, but do not implement one identical edge.
- Native is a family of partial operation domains, with some expansions creating
  further Access/Native calls. A provider name is not proof of universal capability.
- Logical planning currently does not consume later storage/execution choices.
  Renaming a crate to “planner” or “physical” cannot introduce that feedback.

Use source-oriented `*-lowering` for compiler transformations, `policy`/`choose_*`
for decisions, explicit host/observation names where they differ, and data nouns
for runtime structures. Keep concise product names and do not add wrappers merely
to make a naming scheme appear uniform.
