# TPC-H i64 input-column decode audit

## Scope and method

Analysis only; no Rust edits, builds, tests, formatter runs, or measurements were performed. The companion `DECODE-COLUMNS.tsv` has exactly the 19 requested input columns. Query IDs refer to `features/workloads/src/queries/retail/tpch/retail_<id>.rs`, not automatically to the complete standard TPC-H query.

Authority: `STORAGE.md` §1 and §§10–12; `PLANNING-REDESIGN.md` contract 7. R means an opaque authored Rust expression reads a logical value. C means relational-only use (join, anti-join, where, group key, distinct/line identity); it is eligible for code execution under the representation's stated Eq/Ord laws, not proof that today's runtime actually keeps it encoded. Final answer exposure is P. A column can be C during execution and P at the end. An output-purpose `.scaled()` inside a rule is still R, not P-only. There are **no target columns whose authored rule use is exclusively bare output without a relational role or Rust conversion**. In particular c_acctbal (h10), s_acctbal (h02), and o_totalprice (h18) are output-purpose but explicitly Rust-read.

Method A for every query below: inspect the current authored relation-to-variable bindings, opaque `if`/`let`/computed heads, relational `where`, group/identity retention, and final versus intermediate `.map` consumers. Method S: extract declared carriers from saved `sequence_input` in `experiments/gpu/compare/performance_gpu.json`, both SF1 and SF10. The saved artifact contains no `rust_reads` fields; it cannot serve as current free-variable evidence. Current driver evidence is `experiments/gpu/tpch/src/source.rs:577–598` (scalar codecs only for relational-only reads) and `experiments/gpu/tpch/build.rs:121–165,319–334` (loader schema, u32 domain types, and explicit identity/encoded facts). These facts take precedence over assuming that an i64 spelling means an identity value. This audit did not regenerate plans.

The snapshot is historical: its cpu_query uses `if` where current catalog uses `where`, and historical scalar arithmetic appears rewritten to coefficients. This is not authorization to rewrite opaque Rust today. Current driver imports authored queries and protects scalar Rust reads. Staged host `.map` key copies may require logical values in that implementation; immediate re-use in relations is avoidable reorganization (I), not final publication (P). Decoding before subsequent relational processing without an actual opaque read is V; retain codes across stages and publish logical values only at the final boundary.

## Coverage and historical carrier evidence

There are 27 authored query files and 27 query IDs at each of SF1 and SF10 in the saved artifact. h17 is absent. There is no full h21: only h21_positive. h04_not_exists and h07_block are variants; d19/d27/d72_inner/d85 are explicitly TPC-H-derived shapes, not TPC-DS semantics. Do not assign standard-Q3 revenue to h03, Q5 revenue to h05, Q7 revenue to h07, Q8 market share to h08, Q9 profit to h09, Q16 counts to h16, or Q22 account-balance arithmetic to h22.

Saved h02/h11/h13/h15/h18/h20 are marked ran but have `cpu_query: null`, no `sequence_input`, and `pipeline.complete: false`. They support historical run status, not a current checked Sequence representation claim. h14/h19 are `translate rejected` in the snapshot; their current authored sources have changed and this report makes no new execution-success claim. Other queries have saved Sequence inputs. For target columns these show i64 everywhere except h05's u32 customer/order/supplier domain keys. Missing Sequence entries are unknown carriers, not assumed i64. A saved run success does not establish that all work executed on the GPU.

Current `dictionary_types` records string dictionaries as u32, but that does not globally turn these 19 numeric inputs into u32. The driver's domain profile explicitly selects u32 Id carriers, while its I32 profile selects i32. Relational scalar codecs use the manifest's type; opaque Decimal operations must retain an identity-compatible Decimal representation or run at host. A proposed i32 coefficient is a **candidate physical value carrier**, not permission to substitute i32 for the authored Decimal type or rewrite `.scaled()`.

## Value widths, carriers, and scaling

TSV `bits` is SF1/SF10 logical-value width, using the supplied measurements: balance 21 signed; customer 18/21; discount 4; price 24; line number 3; order key 23/26; part 18/21; quantity 13; supplier 14/17; order total 26; availability 14; cost 17. Fixed widths are repeated across scales. These are supplied measurement evidence, not measurements rerun here; signed balance widths include sign. They are not average compressed bits per value. `STORAGE.md:425–436` independently distinguishes FOR/delta/dictionary sizes from plain value widths.

All 19 supplied SF1/SF10 value ranges fit signed i32. Possible byte-aligned storage carriers are u8 (discount/line number), u16 (quantity/availability and SF1 supplier key), u32 (other nonnegative values), and i32 (balances). Small carriers do not imply equally small arithmetic. FOR offsets and dictionary codes have different widths, and reconstructing base+offset or resolving a dictionary is a decode even if both sides fit i32. Raw code/byte transfers are not decode.

For C-only keys, prefer shared-domain encoded/dense carriers, not i32 logical-value materialization: u32 for customer/part/order keys; u16 at SF1 and u32 at SF10 for supplier keys; u8 for line-number identity. Preserve common domain assignment across join sides. The TSV's i32 feasibility statements describe value ranges, not a recommendation to decode these keys. h11's `*part_key` and `*supplier_key` computed heads are syntactic Rust reads under contract 7, but semantically only copies: a code-preserving relational projection would remove the need for logical decoding. Until that authored/representation change is made, do not silently feed domain ordinals into opaque i64 Rust.

Every TSV row states its own accumulator and i32-expression conclusion. Arithmetic bounds use the supplied bit widths rather than unobserved exact extrema. For example, price times a dbgen discount coefficient <=10 is <=167,772,150 (the looser 4-bit bound is 251,658,225); filtered h06 discount <=7 gives <=117,440,505. Exact measured maxima could tighten these bounds, but are not supplied by the bit counts. Likewise an approximately 1.3-billion cost/availability product is not asserted as measured here: the independent bit-width bound already proves the product fits signed i32. Authored `.scaled()` yields i64 before multiplication; h11/h20 explicit `i128::from` occurs before multiplication. Narrow physical storage does not alter those Rust cast semantics.

Order key maximum is approximately 6,000,000 × SF: identity values exceed u32 at integer SF716 (and signed i32 already at SF358). Dense rank over approximately 1,500,000 × SF orders fits u32 until roughly SF2800 (the arithmetic boundary is approximately SF2863, subject to code reservation). Ordinal inversion at final answer is P; inversion before relational processing is not. Other target entity keys remain below 2^32 for SF <= 20000 (part: 200000×SF; customer:150000×SF; supplier:10000×SF), but may exceed **signed** i32. Lineitem row positions/counts can exceed u32 much earlier than dense order ranks: roughly 6M rows/SF. A key-width argument cannot narrow row offsets, counts, or aggregate state automatically.

## Arithmetic and accumulator widths

* h01: individual quantity/price coefficients fit i32; sums require i64. Worst-case loose SF10 price sum is about 60M × (2^24−1), far beyond i32. Count is authored usize, target-width dependent, not inherently u32.
* h06: price × discount fits i32 under the supplied 24-bit price and 4-bit discount bounds: (2^24−1)×15 = 251,658,225. The qualifying discount is only 5–7. Quantity/discount comparisons fit i32. Global revenue sum remains i64.
* h10/h14/h15/h19: price × (100−discount) fits signed i32 for nonnegative discount in the TPC-H domain: at most (2^24−1)×100 = 1,677,721,500. This requires the domain bound, not simply “both operands fit i32.” Multiply after appropriate extension; narrowing multiplication operands to u16 would be wrong. Revenue sums and h15 maximum over sums remain i64/Option<i64>. h19 quantity tests fit i32.
* h02: scaled cost and balance fit i32; min has no additive growth, although authored state is Option<i64>. Some(cost.scaled()) and the output balance are Rust reads. No sum accumulator for s_acctbal.
* h11: the supplied independent nonnegative bit bounds narrowly prove an i32 product: (2^14−1)×(2^17−1) = 2,147,336,193, just below i32::MAX. Per-part/global sums still require i64; do not extend this conclusion to arbitrary i64 loader values. The authored comparison widens **before** multiplying by 10000 using i128; a large global/part aggregate can overflow i32, and generic i64×10000 is not safe without bounds. Preserve the explicit i128 operation.
* h18: input quantity and total-price projection fit i32. Standard dbgen has at most seven lines/order, so its per-order quantity sum also fits i32 (7×5000 = 35000); authored sum remains i64 and this cardinality bound is not established merely by a width fact. o_totalprice is not summed here.
* h20: availability × 200 fits i32 under 14-bit bound (3,276,600), but the comparison operand is an i64 shipment aggregate; use its width, not the input quantity width. Authored code explicitly converts both sides to i128 before comparison. Shipment sum remains i64 unless a separate group-cardinality proof is recorded.
* h12: 0/1 per-line expressions fit i32; high/low sums are i64. h13 uses usize count, not arithmetic on order-key values. h11's explicit key dereference heads are Rust copies, not multiplication of keys.
* Other listed queries have no target-column arithmetic: i32 suffices for SF1/SF10 identity comparisons but code-domain joins can avoid logical decoding entirely. No universal i64 aggregate guarantee is made for arbitrary SF or arbitrary input; aggregate range grows with cardinality. Widen **before** multiplication/addition, not after an overflowing narrow intermediate.

Thus “all inputs fit i32” is true only for the supplied SF1/SF10 values; “all per-row expressions fit i32” is false as a blanket statement because staged aggregate comparisons operate on wide derived values and authored i128 expressions must remain verbatim. The numeric bounds above are feasibility analysis, not compiler authorization or a source-change proposal.
