\section{Query semantics and host assumptions}
\label{sec:scope}
\subsection{From valuations to answers}
\label{sec:valuations}
A valuation assigns values to query variables. With rows $R(1,2)$ and $S(2,3)$,
the query $\mathsf{answer}(x,z)\leftarrow R(x,y),S(y,z)$ is satisfied by
$\nu=\{x\mapsto1,y\mapsto2,z\mapsto3\}$, yielding $(1,3)$.
The repeated $y$ expresses equality without choosing an atom order.

Following AHV~\cite[Sections 3.1--3.3 and 4.2]{ahv}, fix disjoint sets of
attributes $\att$, variables $\var$, relation names, and values $\data$.
A schema $R[U]$ has finite \emph{sort} $U\subseteq\att$ and arity $|U|$.
A named tuple is a function $t:U\to\data$; $t[V]$ restricts it to $V$.
A relation is a finite set of such tuples, and a database $I$ assigns one
to each schema. The compiler also records declared column order and Rust
types in $\Sigma(R)=\langle A_0:\tau_0,\ldots,A_{k-1}:\tau_{k-1}\rangle$.
Membership written as an ordered row uses this declared order.

A valuation $\nu:X\to\data$ has variables as its domain, extends constants
by $\nu(a)=a$, and acts coordinatewise on tuples. For a range-restricted CQ,
\[
 \sem q_I=
 \{\nu(\bar h)\mid \nu:\vars(q)\to\data,\
       \nu(\bar u_i)\in I(R_i)\text{ for every body atom }R_i(\bar u_i)\}.
\]
This is the semantics of the classical fragment. Rust computations require
the host assumptions below.

\subsection{Valuation relations and named algebra}
To represent valuations as named tuples, fix an injection
$\iota:\var\to\att$ and set $\widehat\nu(\iota(x))=\nu(x)$.
For a conjunction $C$ of relational atoms, the notes' \emph{valuation relation}~\cite{notes} is
$\Val_I(C)=\{\widehat\nu\mid I\models C[\nu],\ \dom\nu=\vars(C)\}$.
Below, $x$ abbreviates the corresponding attribute $\iota(x)$.
Thus valuations assign query variables; named tuples supply relation attributes.

For relations $L:V$, $M:W$, define
\[
\begin{aligned}
 L\bowtie M&=\{t:V\cup W\to\data\mid t[V]\in L,\ t[W]\in M\},\\
 \pi_U L&=\{t[U]\mid t\in L\}\quad(U\subseteq V),&
 L\ltimes M&=\pi_V(L\bowtie M),\qquad \mathbf1=\{\langle\rangle\}.
\end{aligned}
\]
These are AHV's named join, projection and semijoin~\cite[Sections 4.4 and 6.4]{ahv}.
Write $t\sim u$ for agreement on their common attributes. Empty common sort
gives a Cartesian product; $\pi_\emptyset L$ is $\mathbf1$ for nonempty $L$
and empty otherwise. For injective $m:V\to\att$, renaming $\delta_m(L)$
replaces each attribute $A$ by $m(A)$ without changing its value.

\begin{lemma}[Conjunction as natural join]
$\Val_I(C_1\land C_2)=\Val_I(C_1)\bowtie\Val_I(C_2)$.
\end{lemma}
\begin{proof}
A satisfying valuation restricts to compatible valuations of both conjuncts.
Conversely, compatible valuations have a unique union satisfying both.
\end{proof}
A distinct-variable atom is therefore its input relation renamed by argument
position. Repetitions, constants and computed arguments require additional
constraints (C/A-*). For distinct head variables $\bar h$ and $H=\set(\bar h)$,
\[
 \sem q_I=\operatorname{out}_{\bar h}(\pi_H\Val_I(C)),\qquad
 \operatorname{out}_{\bar h}(L)=
 \{\langle t(h_1),\ldots,t(h_m)\rangle\mid t\in L\}.
\]
Projection selects attributes; out fixes answer order. Computed or repeated
head expressions instead act on each valuation.

\subsection{Assumptions for relational compilation}
A host judgment
$\langle e,\rho,\sigma\rangle\Downarrow_H(v,\sigma',\alpha)$
evaluates Rust expression $e$ in binding environment $\rho$ and store $\sigma$,
returning value $v$ and events $\alpha$. Panic and divergence are also possible.
The relation $v\simeq_\tau a$ connects Rust values with abstract values;
input fields are borrowed, while computed bindings can be owned.

\begin{definition}[Admissible relational host, $\mathcal H_{\rm rel}$]
\label{def:host}
On reachable inputs:
\begin{enumerate}
\item Expressions and pattern matches terminate normally; let patterns are
irrefutable at their elaborated types.
\item Each expression represents a mathematical function $\bar e$ of its
logical inputs, independent of store, addresses, aliasing, enumeration,
and irrelevant environment extensions, with no observable effects.
\item Equality, hashing, cloning and dropping terminate silently. Rust equality
agrees exactly with equality of represented values; equal values hash equally;
clones preserve values. When used, sorting implements a consistent total order silently.
\item Generated Rust resolves and type-checks, including ownership and
captures, and implements the intended variable interpretation. Resource
exhaustion is outside the finite-value model.
\end{enumerate}
\end{definition}
These are theorem premises, not properties established by Syn or Rust trait
bounds. They give $\sigma_eL=\{t\in L\mid\bar e(t)=\mathsf{true}\}$ and
$\operatorname{ext}_{N,e}L=\{t\cup\bar e(t)\mid t\in L\}$, where
$\bar e(t):N$ is the named tuple of fresh pattern bindings.

\subsection{What each preservation claim means}
For a completed finite cursor $s$, $\operatorname{Rows}(s)=\set(s)$.
Set preservation permits different enumeration. Local cursor preservation
can additionally relate each poll and its callback events.
For a finite client protocol $d$ (build, query, next, drop), let
$\mathcal B_d(P,I,\sigma)$ contain the admitted behaviors of $P$:
answers, host events and stores at each request. For exhaustive clients,
$O_{\rm set}$ and $O_{\rm seq}$ retain the complete answer set and sequence;
$O_{\rm client}$ also records per-request effects and permits partial demand.
$\operatorname{Obs}_d$ denotes the chosen observation. On the edge's admitted
inputs and stores, refinement for client class $\mathcal D$ means
\[
 T\preceq_{O,\mathcal D}S
 \quad\Longleftrightarrow\quad
 \forall I,\sigma,\ d\in\mathcal D.\quad
 O(\mathcal B_d(T,I,\sigma))\subseteq O(\mathcal B_d(S,I,\sigma)),
\]
where $O$ acts pointwise through the representation relations.
Finite refinement claims require response totality:
both behavior sets are nonempty and every admitted execution responds
successfully to each request. A failing target cannot refine a source merely
by having no successful behavior. Clients stop polling at first exhaustion;
arbitrary Rust iterators need not be fused.

\begin{counterexample}[Equal clause order does not preserve effects]
\label{cx:effects}
Let $R=\{(10),(20)\}$, \code{tick(x)} increment and return a counter initially zero,
and \code{latest(n)} test whether the counter still equals $n$:
\begin{lstlisting}
answer(x) :- R(x), let n:i32 = tick(x), if latest(n);
\end{lstlisting}
Lazy evaluation interleaves tick and guard, retaining both rows. Materialized
evaluation completes both ticks first, retaining only the row assigned 2.
Lazy build performs no ticks; materialized build performs two. The compiled
\code{formal_counterexamples.rs} tests witness both differences.
\end{counterexample}

Theorems below concern the mathematical rules under their stated premises.
Rust type/ownership adequacy (C-Rust), binding resolution (C-Resolution),
simulation of concrete transitions including rejection (C-Conformance), and
panic/divergence/destruction semantics (C-Effects) remain open obligations.
The arbitrary-Rust source also lacks a cross-route operational contract.
Negation and aggregation parse but have no successful lowering; graph-region
optimization, cardinality estimation and WCOJ remain unimplemented.
