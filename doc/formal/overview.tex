\section{An authored expansion to review}
\label{sec:overview}
\textbf{This is an expected expansion, not output captured from the current
compiler.} It makes the boundary in Section~\ref{sec:ix-physical-redesign}
concrete. The fixture is a local fragment with two consuming positions in a
larger fixed RA plan; it does not prescribe a complete query schedule.

\paragraph{1. Logical plan and IX.}
Let $H(l)=[a]$, $H(r)=[a,b]$, $H(m)=[c]$, and $H(s)=[c,d]$.
The two operators are $j_0=l\bowtie r$ and $j_1=m\bowtie s$.
IX records the required index on each right operand and names every use.
The exact local RA and IX programs are \code{input.ra} and
\code{expected.ix} in \path{doc/ix-physical/}.
The definition $i_0$ is reusable by another occurrence requiring $r$ on
$[0]$; an access to a pruned version of $r$ would require its own descriptor.
Physical lowering reads these references. It does not repeat intersection
analysis to decide which index each occurrence uses.

\paragraph{2. Selection produces Physical.}
The host supplies $r$ as a hash-indexed relation and $s$ as an ordered-indexed
relation. The authored physical policy binds their exact versions, the two
slice inputs, and the required indexes to external provider instances.
It also selects the lowering for each of the two join definitions. The complete
bound local program is \code{expected.physical}; it retains IX and appends
the relation, index, and lowering bindings. No loop or index construction has
been emitted at this boundary.
The illustrated paths stand for external definitions, not implemented exports
or cases hardcoded into the compiler.
Their delivered declarations determine which representation and access rules
apply. The wire slot \code{choose_physical!} invokes the selected policy
implementation. Its expected immediate output is \code{expected.choose.rs}:
a call to \code{realize_physical!} containing the bound Physical program.
This call makes the completed selection inspectable before realization begins.

\paragraph{3. Realization follows the bound program.}
The host environment supplies borrowed slices for $l,m$, a borrowed hash map
for $r$, and a borrowed ordered map for $s$, as written in
\code{environment.txt}.
The map entry $(a,[b_1,\ldots,b_n])$ represents rows
$(a,b_1),\ldots,(a,b_n)$; the ordered map has the analogous meaning.
The exact completed target is \code{expected.rs}, reproduced in
Section~\ref{sec:ix-physical-redesign}. The wire slot
\code{realize_physical!} dispatches the already selected lowerings and provider
definitions; it receives no policy. Existing relation storage realizes both
requested indexes, so preparation binds their views without rebuilding maps.
The Access sources contain the concrete lookups supplied by those definitions.
The Access heads yield \code{(a,b)} and \code{(c,d)}: tuples of references
whose values decode to logical result rows. No owned composite row or payload
clone is needed. The two map APIs happen to share lookup spelling; this does
not make their declarations interchangeable. Auxiliary indexes over an existing
row source remain a separate construction example.

Obtaining provider declarations may require administrative macro callbacks.
Therefore the completed target is not asserted to be the output of one Rust
macro expansion. A standalone callback fixture demonstrates that mechanism;
it does not constitute an integrated compiler trace for this query.

\paragraph{Meaning and acceptance.}
For $r=\{(1,10),(1,11),(2,20)\}$, $s=\{(3,30),(3,31),(4,40)\}$,
$l=\{1\}$, and $m=\{3\}$, the observations are
$j_0=\{(1,10),(1,11)\}$ and $j_1=\{(3,30),(3,31)\}$.
Every matching payload must remain available; retaining one representative
per indexed-column tuple is incorrect.

The proposed artifact stops at concrete physical preparation and Access
quotations. Push/pull placement is deliberately unsettled. Acceptance
requires the compiler's actual expansion to match the expected tokens,
ignoring only whitespace and spans, as well as preserving these results.
The current compiler fails the index-definition/use and Physical boundaries;
its earlier runtime tests do not establish conformance to this redesign.
