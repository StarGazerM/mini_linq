\section{Replacement boundaries}
\label{sec:extensibility}
The provider environment $\Omega$ is open. Extending it with a fresh provider
path must not require adding a data-structure case to the common compiler.
That compiler dispatches through $\Phi_R$, $\Phi_I$ and $\Lambda$; a replaceable
policy $\eta$ records their choices in Physical IR from IX demands and
available representations. Realization consumes that fixed program without
invoking the selection policy again.
An explicit configuration is one possible policy input. This document does
not prescribe a cost model or infer semantic laws from an opaque Rust type.

\paragraph{Two scopes of wiring.}
An import alias binds \texttt{choose\_physical!} to the physical-selection macro
used for a query; another binds \texttt{realize\_physical!} to the realizer.
The policy chooses individual provider instances and definition lowerings.
These are
different scopes: changing one index's provider must not silently change every
relation or index. The policy may deliberately choose one provider throughout,
but uniformity is its decision rather than a limitation of the interface.

\paragraph{A provider owns its interpretation.}
A provider definition supplies the applicable construction and access
expansions together with their representation laws. Each use is dispatched
through the binding that constructed its representation; each RA definition
uses its recorded lowering. Their rules state compatibility premises against
the corresponding relation version and representation in $\Gamma$.
Unsupported domains must be rejected; applicable Rust type checks occur after
expansion. No generic semantic proof procedure is assumed.
The hash/sorted rules in Section~\ref{sec:ix-physical-redesign} are provider
instances, not an exhaustive syntax of physical choices. A block or trie
provider need not pretend to implement the identical lookup interface: it must
establish the laws required by the physical rules that consume its operations.

\paragraph{Provider declarations and algorithms.}
A BYODS-like declaration DSL could generate macro dispatch, argument binding
and Rust trait adapters from a provider definition. Such convenience syntax
must preserve independent provider bindings and cannot establish semantic laws
merely by declaring a capability tag. Its concrete syntax remains unspecified.
A storage provider exposes storage operations; a compiler rule composes them
to implement an RA operation. Selecting a trie does not itself select or
implement WCOJ. Provider callbacks are administrative steps within realization;
they do not require a separate complete compiler pipeline for each structure.
An explicit provider dialect is justified only with a specified semantic
boundary. Algorithm extensions must respect the admitted IX and Physical
boundaries; multiway lowering and push/pull placement remain future work.

\paragraph{Implementation organization.}
Provider crates may depend on their own storage implementations. The common
compiler should not import every concrete provider in order to dispatch.
Feature and dependency tests should demonstrate this extension boundary;
representation arguments establish correctness. Storage contains data
structures and their minimal access APIs, not a runtime RA interpreter.
