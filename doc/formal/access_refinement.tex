\section{Metadata pruning requires an exact residual}
\label{sec:access-refinement}
The concrete provider examples currently specify exact hash and sorted access.
This section records the semantic obligation for a future block realization;
it does not implement a block provider, add a compiler stage, or bypass IX.
Approximate membership and block metadata alone do not satisfy exact lookup.

\paragraph{Current-view semantics.}
Let $V$ be the handles of the current source version, $\rho(h)$ the row decoded
from its original owner, and $C$ the indexed columns written in IX. For a lookup
value $v$, define
\[
 E_v=\{h\in V\mid\pi_C(\rho(h))=v\}.
\]
A metadata-based candidate procedure $\mathcal C$ is sound when
\begin{equation}\label{eq:candidate-cover}
 E_v\subseteq\set(\mathcal C(V,v))\subseteq V.
\end{equation}
Its handles must remain valid for the originating source version. Selecting a
view cannot reintroduce a row removed from that view, even if the original
payload and metadata are shared. The exact residual tests full indexed-column
tuple equality for each candidate.

\begin{mathpar}
\Rule{Candidate-Exact}{E_v\subseteq\set(\mathcal C(V,v))\subseteq V}
 {\{h\in\mathcal C(V,v)\mid\pi_C(\rho(h))=v\}=E_v}
\end{mathpar}
This is a semantic refinement law, not a rule choosing a new physical provider.
When occurrence-preserving access is required, candidate traversal must also
avoid duplicating handles. Rust type checking cannot establish candidate coverage.

\paragraph{Zone maps.}
For each immutable block $b$ and indexed coordinate $c_j$, let
$[\min_b(c_j),\max_b(c_j)]$ enclose all original rows in that block. A point
lookup keeps the block exactly when its conservative test is true:
\[
 m_v(b)=\bigwedge_j\bigl(\min_b(c_j)\le v_j\le\max_b(c_j)\bigr).
\]
The candidates are current handles in kept blocks. A matching row satisfies
every interval test, proving the left inclusion in \eqref{eq:candidate-cover}.
Coordinate tests can admit false positives, particularly for composite columns;
the exact residual is still required. Original block bounds remain sound for
any selected subset of the original rows, although they may become less precise.

For semijoin pruning, let $K$ contain the exact RHS indexed-column tuples.
At coordinate $j$, the interval $[\min_K(j),\max_K(j)]$ encloses every value in $K$.
Here $c_j$ is the corresponding left physical coordinate, obtained by translating
the written RHS IX columns through the operand headings. Write $C_l$ for this
ordered left-coordinate list; this translation does not rederive index demands.
The conservative block guard is
\[
\begin{aligned}
 m_K(b)&=(K\ne\varnothing)\ \land\bigwedge_j o_j(b),\\
 o_j(b)&=\min_K(j)\le\max_b(c_j)
                \land\min_b(c_j)\le\max_K(j).
\end{aligned}
\]
The residual is exact membership $\pi_{C_l}(\rho(h))\in K$ using the realized RHS
index. With no join columns, $K$ is either empty or contains only $()$; the
empty conjunction is true. With empty $K$, no block is admitted.

\begin{lemma}[Conservative rejection]
If the block and RHS bounds enclose the stated rows and tuples, rejecting a block
with $\neg m_K(b)$ cannot discard a semijoin witness.
\end{lemma}
\begin{proof}
A matching current row has one tuple in $K$. At every indexed coordinate, that
value lies in both the block interval and the RHS interval. The intervals must
overlap, so the block guard holds. Exact membership then removes all false
positives among the retained current handles.
\end{proof}

Physical must record the metadata-pruning lowering in $\Lambda$ and compatible
relation/index bindings in $\Phi$. Realization checks and follows those choices;
it cannot silently fall back to full traversal. The physical binding of the
pruned relation must expose blocks before payload reads
can be skipped. Reading all rows into an ordinary map and then evaluating zone
guards cannot avoid those earlier reads. A future realization must therefore
specify its block source, metadata, residual, and lifetime rules together and
provide an authored concrete expansion. The present hash/sorted fixture does
not claim to implement that extension.
