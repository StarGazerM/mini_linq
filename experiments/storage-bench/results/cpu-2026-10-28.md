# CPU storage codec measurements — 2026-10-28

## Scope and protocol

Rust standalone crate `experiments/storage-bench/cpu/`; AMD Threadripper PRO 5945WX (12 cores / 24 logical CPUs), resident data, t1 and Rayon t24. Release build: `RUSTFLAGS="-C target-cpu=native"`, `opt-level=3`, thin LTO, one codegen unit; compiled with `nice -n 19` and `-j1`. The JSON contains compiler/CPU/driver metadata, current CPU MHz, GPU clock reports, `uptime`, top CPU processes and compute tenants before/after each interleaved measurement group. Groups with any GPU compute tenant or an external process at ≥20% lifetime-average CPU according to `ps` are deferred/discarded and repeated. This boundary check cannot detect all transient or low-average contention.

Every variant has five warmups and 21 retained samples, with a rotated variant order per round. Every sample and warmup is checked exactly against the plain reference outside timing. CIs use 2,000 deterministic nonparametric bootstrap resamples; ratio CIs resample paired round indices and divide medians. Ratios below 1 favor the encoded variant. CIs characterize these runs, not cross-machine reproducibility.

Bit packing: 1024-row blocks, 16 interleaved u64 lanes; const-generic unpack specializations for each width 0–64. The inner contiguous lane loop has uniform shifts, making vectorization possible without per-value width dispatch. Byte offsets are u8/u16/u32 (u64 fallback only exercised by codec correctness tests), with per-block minimum base. Dictionary codes use one global ceil(log2 distinct) width; byte dictionary codes use global u8/u16/u32 width. All dictionaries are sorted. M1 measures reconstruction before predicates, not specialized code-domain predicates.

Tuning effort: the same block size and fixed chunking were selected once, with no measured-result-driven tuning for any codec. Native plain scans directly access native arrays; compressed scans unpack stack blocks. M1/M5 task chunks are 65,536 rows, M2 chunks are 1,024 probes, M3 merge chunks are 65,536 output rows and decode/encode blocks are 1,024 rows. No thread affinity or NUMA binding was applied. M3 uses preallocated scratch and output buffers for both variants; re-encoding recomputes block min/max and checks the preconfigured output width.

M1 Q6 uses real SF1 data and a tenfold tile, with shipdate [1994-01-01, 1995-01-01), discount [5,7] cents, and quantity <2400 cents. Extendedprice is accessed only for qualifying rows. Synthetic values are deterministic uniform w-bit integers in [0,2^w); actual achieved selectivity is included in each case (the w=4 domain cannot express 1% or 15% exactly). M2 uses real orderkey→row positions and sorted partkey→suppkey, identical binary-search directories, 65,536 deterministic probes with exactly half hits; misses are above the maximum key. All six payload×offset combinations are interleaved in each M2 group; its common ratio baseline is plain payload with u32 offsets. An earlier offset-separated run was superseded, not used for the reported comparisons, and retained in the JSON for provenance. M3 uses sorted u64 sequences 3*i and 29*i+1, and verifies every merged and decoded re-encoded output element. M5 uses the actual read-only DuckDB SF1 returnflag/linestatus columns, exported in dbgen order. The baseline hashes borrowed String-backed key pairs (no per-row string cloning), while u8 combined codes directly index six count/sum groups; sums use extendedprice.

**Bandwidth qualification:** reported effective GB/s counts logical encoded input accesses, base/width metadata, and dictionary dereferences, not measured DRAM traffic. M1 predicate columns are fully read and prices are late materialized. Repeated scalar accesses count repeatedly. Dictionary lookup locality, cache-line traffic, allocator headers, scratch writes, and hardware prefetch traffic are not observed. M3 GB/s counts input bytes only, excluding output and decode intermediates; M2 reports probes/s and does not claim bandwidth. Resident byte counts are encoded input sizes, not complete process RSS. Compression-build costs and load/transfer are excluded.

## Observed crossovers and contrary outcomes

- **t1 count crossover:** byte offsets clearly win at 4–16 bits and clearly lose at 20–32 bits at both sizes and all selectivity targets. The measured crossover is bracketed between 16 and 20 bits, coinciding with the u16→u32 storage step.
- **t1 FOR count:** no winning width was observed from 4 through 32 bits, despite fewer input bytes.
- **t24 count:** bytes and FOR clearly beat plain at every tested width, size and target selectivity. No losing crossover is observed through 32 bits; results do not establish behavior above 32 bits.
- **Q6 t1:** bytes/plain time ratios are 0.651 at n=6,001,215, 0.641 at n=60,012,150. Byte truncation is the fastest median in each Q6 case.
- **Q6 t24:** bytes/plain time ratios are 0.480 at n=6,001,215, 0.573 at n=60,012,150. Byte truncation is the fastest median in each Q6 case.
- **Q6 versus count:** t1 FOR improves the real multi-column Q6 shape even though it loses every t1 single-column count sweep. [INFERENCE] The tradeoff depends on predicate work, column widths and late-materialized access, not merely a universal “decode ns/value.” The experiments do not isolate those contributions individually.
- **M3 sorted-1000000-100000 t1:** decode→merge→re-encode costs 4.27× plain time (95% CI [2.88, 4.30]). [INFERENCE] Input-byte savings do not repay decode, intermediate traffic and re-encoding in this implementation.
- **M3 sorted-1000000-100000 t24:** decode→merge→re-encode costs 2.73× plain time (95% CI [2.63, 2.95]). [INFERENCE] Input-byte savings do not repay decode, intermediate traffic and re-encoding in this implementation.
- **M3 sorted-16000000-1600000 t1:** decode→merge→re-encode costs 4.24× plain time (95% CI [4.22, 4.27]). [INFERENCE] Input-byte savings do not repay decode, intermediate traffic and re-encoding in this implementation.
- **M3 sorted-16000000-1600000 t24:** decode→merge→re-encode costs 2.30× plain time (95% CI [2.27, 2.32]). [INFERENCE] Input-byte savings do not repay decode, intermediate traffic and re-encoding in this implementation.
- **M2 orderkey-positions t1:** fastest median is plain_offset32 at 9.94 Mprobes/s. Plain u64/u32-offset time ratio is 1.033 [1.002, 1.053]. The offset CI excludes 1.
- **M2 orderkey-positions t24:** fastest median is plain_offset32 at 164.75 Mprobes/s. Plain u64/u32-offset time ratio is 1.006 [0.925, 1.081]. The offset CI overlaps 1; this run does not resolve an offset-speed winner.
- **M2 partkey-suppkey t1:** fastest median is bytes_offset32 at 8.31 Mprobes/s. Plain u64/u32-offset time ratio is 1.031 [1.018, 1.047]. The offset CI excludes 1.
- **M2 partkey-suppkey t24:** fastest median is plain_offset32 at 131.80 Mprobes/s. Plain u64/u32-offset time ratio is 1.013 [0.981, 1.049]. The offset CI overlaps 1; this run does not resolve an offset-speed winner.
- **M2 scope:** compressed payloads do not uniformly lose: byte payload/u32 offsets wins the t1 partkey→suppkey case, while several other differences are unresolved. [INFERENCE] Longer expansions and smaller payload working sets can offset decode cost. This refutes a universal “index runs must never be compressed” conclusion from these measurements alone.

## Interpretation and limits

- The width table is the target-specific measured crossover evidence. A smaller resident representation alone is not evidence of a scan win; decoding, dictionary reconstruction, and cache behavior are included in the observed ratios.
- [INFERENCE] Where compressed representations lose despite lower logical bytes, decode/control costs and/or lower parallel efficiency outweigh the saved input traffic. This study does not have hardware performance-counter attribution, so it cannot identify a unique microarchitectural cause.
- [INFERENCE] Dictionary reconstruction may be especially unfavorable for high-cardinality uniform values because it introduces dependent dictionary reads. M5 avoids reconstruction by executing on codes; its comparison is intentionally a different question.
- [INFERENCE] Differences between t1 and t24 or nonmonotone width outcomes can reflect the 64 MiB aggregate L3, two NUMA nodes, SMT, scheduling, and contention. Ratios with CIs overlapping 1 do not establish a winner.
- M2 answers the payload/offset question with an unchanged directory and workload. M3 includes decode and re-encode, but excludes allocation/build costs. Neither result justifies a universal storage-role rule beyond the measured cases.
