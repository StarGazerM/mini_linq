TPC-H-derived benchmark methodology

Scope and query authorship
The current inventory contains 29 independently named retail-derived and canonical
kernels over dbgen tables, including grouped and multistage kernels. Their SQL
peers are authored with each module. The synthetic retail corpus is unchanged.
The four d-prefixed kernels map their TPC-DS-inspired relation roles onto real
TPC-H dbgen relations; each source documents the mapping. They are not TPC-DS
queries. All filters execute inside the measured query, not during export.

tpch/coverage.tsv records all 22 canonical full-query assessments.
Q6 and Q19 have authored SQL and MiniLinq/aggregate compositions. Exact missing
ordered-result/top-k support excludes 18 complete queries; no required ordering
or limit is silently dropped. Q14/Q17 have a documented floating-result and
exactness-contract limitation. tpch/numeric_contract.txt gives the details. String
LIKE patterns, HAVING, AVG composition and COUNT DISTINCT are not falsely
reported missing merely because their SQL keywords are absent.

Compile-only CPU gate
From features/workloads, run:
  cargo xtask compile-tpch
Or from the repository root:
  cargo run --locked --manifest-path features/workloads/xtask/Cargo.toml --features oracle -- compile-tpch
This opt-in Main batch gate builds all 29 catalog kernels as ordinary release
timing workers, including both default and par (Sequence Tasks) and every other
authored CPU configuration. It uses the same sources, compiler pipeline and
target/bench crate/build cache as the benchmark; CARGO_TARGET_DIR, when set,
places compiled workers under its tpch-workers subdirectory. It builds neither
counting nor profiling variants. Each worker's metadata-only describe command
must advertise default and par; a build or missing-route failure fails the gate.
The xtask enables its existing oracle feature for shared benchmark plumbing,
but does not invoke DuckDB, dbgen, projection export, data loaders, or queries.
CPU compilation requires no dataset: default/par use the checked-in neutral
authored/tpch-sf1-evidence.json document. Unlike bench --runs 0, this is
compilation coverage, not an exact-answer or runtime gate.
The command accepts no options, so --query/--config cannot accidentally narrow
the catalog coverage. New CASES entries are included automatically.
Keep this release-build matrix in Main's explicit batch, outside the default
regression inventory and quick tier: compiling all authored routes in 29
independent workers is substantially more expensive than a focused contract
test. Run it before CPU benchmark batches and after compiler/Tasks changes.

Data and correctness
The xtask oracle uses DuckDB tpch CALL dbgen at SF 0.1, SF 1 and SF 10. Generated
DuckDB tables, per-query projected Parquet files, manifests, executable crates,
Cargo timing reports, answer witnesses and output reports live under target/bench.
Exports contain only declared columns, in declaration order, without filters,
preaggregation or casts. Typed relation_loaders! read the Parquet schemas into
Vec hosts and sort/deduplicate complete declared rows once before query timing.
The file cache is local and engine-version/projection keyed.
Interned loaders borrow Arrow string cells directly into column-local hash
tables. Each source cell is hashed once; table growth reuses cached hashes.
Only distinct dictionary entries allocate text. After input is exhausted,
distinct entries are sorted lexicographically and temporary integer IDs are
remapped, preserving the previous exact codes independently of row/batch order.
Input, sorting, and remapping remain load_ms work; query execution is unchanged.
Column state is sequential for bounded streaming memory, not because final codes
depend on encounter order. Parallel chunk tables would require duplicate text
storage and a merge/remap; that tradeoff is not imposed on small columns.
The byte-scan throughput is a lower-work reference, not an attainable guarantee:
exact sorted codes additionally require deduplication, dictionary allocation,
distinct-value ordering, and integer output writes. The cq-load `intern` release
example reports five interleaved former/new passes and byte scans over a retained
Parquet column, excluding I/O/decompression, and asserts exact row codes.
Every compiler input is a set, unconditionally; no host_set or Sequence key
annotation grants setness. IO owns the boundary: CSV, Parquet and interned
tuple loaders sort/deduplicate full rows in place, and columnar loaders
canonicalize exact projected row positions before publishing encoded columns.
H01 therefore needs no dbgen key premise: duplicate complete seven-column
Lineitem rows collapse, but different full rows sharing an order/line pair
remain distinct. H13's comment filtering and (order,customer) projection remain
inside run(), followed by full-row deduplication of QualifiedOrders; these are
query operations and remain inside every route's query timer. H04 NOT EXISTS
likewise deduplicates its projected LateLineitem during query setup. Dictionary
predicate relations contain one row per selected dictionary code; zone layouts
retain their canonical loaded rows. Hand-built fixtures must canonicalize
their input relations too. Checked neutral row/key evidence remains planning
information, not an input-set proof or a license to infer a narrower semantic key.

For SF 1 and SF 10, every executable/configuration is checked against authored
DuckDB SQL on SF 0.1 before any query measurements. At SF 0.1 the timed workers
check exact answers before sampling. The requested scale is also checked before
each configuration's measured runs. `--runs 0` only verifies: one untimed
exact execution per selected configuration at the requested scale, without
counting workers or DuckDB timing. `--config a,b` runs exactly those names.
Comparison uses sets of complete output tuples. Only columns typed DECIMAL by
DuckDB normalize trailing fractional zeroes; VARCHAR values are unchanged.
No float tolerance is used. Q6/Q19 keep lineitem primary keys through distinct
CQ heads so equal-valued different input rows still contribute to SQL SUM.
Products/sums use i128 coefficients at scale four. Empty scalar SUM yields NULL.
Every timed run must reproduce its warm answer. Two separate untimed counting executions must agree exactly.

Configurations
Every retail query compiles the same authored clauses in these configurations:
- default: the evidence/coarse CQ planner with Masks reductions and default
  recorded Physical decisions; this is already a reduced baseline;
- no-reduce: the written planner with implicit semijoin reduction disabled;
- par: the same authored query with Sequence Tasks decomposition, grading and
  translation, retaining stage-local evidence;
  Default/par attach checked DatasetEvidence through the workload adapter in
  authored/src/tpch_evidence.rs. CPU counts/keys come from checked-in
  authored/tpch-sf1-evidence.json, including standalone generated workers.
  This neutral document was generated once from the SF1 dataset manifest and
  records that manifest's SHA-256 and original path in provenance; no external
  dataset is opened during CPU compilation. Its optional origin-comparison test
  checks row counts and hash when that path exists, otherwise prints a skip message.
  authored/tpch-evidence.json records explicit compiler/table/column mappings
  and authored TPC-H keys (Source::Declared), not measured key certificates.
  GPU automatic planning uses the same adapter with its per-scale manifest and
  explicit stage-file bindings. Scalar domains are deliberately uncertified;
  the adapter does not scan rows, measure statistics, or certify input sets.
  Other CPU routes and Sequence count/bounds advice are unchanged.
  Evidence attachment is the final surface pass, after aggregate/correlated
  contexts expand their checked core holes. It never parses those extensions'
  grammars. The ordinary catalog regression compiles Q06's actual default/par
  dispatch so this boundary is covered without the opt-in compile-only matrix.
- radix and radix_retained: the same-plan provider comparisons described below;
- transfer: the CQ planner's exact forward/backward semijoin schedule, rooted
  at the written outer stream, over its Masks reductions. This configuration
  is not a vectorized blocked-Bloom RPT implementation and does not implement
  RPT+ in-flight adaptive cancellation;
- le: the Lookup & Expand planner;
- le_runs: Lookup & Expand with sorted_runs and retain_lookups Structures rewrites;
- advised: checked stage-local CPU order/reduction advice. Most advice follows
  experiments/gpu/tpch/src/advice.rs without device-only storage choices;
  H05 keeps the CPU cycle-closing order documented below. H10/H14 use the
  grouped GPU route's unreduced written order.
Standalone queries use standalone_configs!, authoring their runner and each CQ
body once. Each query! stage supplies its own advice, applied only by advised,
so that configuration retains per-stage order rather than applying one stage's
order to every rule. Transfer instead selects its planner for every CQ stage
in the same runner, preserving preprocessing and materialization.
The GPU importer unwraps this shared shell without applying the CPU pipeline.
Kernel queries also retain their existing candidates:
- hypergraph: written/coarse planning with tree reductions in eligible acyclic
  scopes and block-aware reductions where applicable; it is not uniformly
  "default plus Yannakakis";
- generic_smallest: fine variable-at-a-time planning, canonical projections and
  smallest intersection driver on H05, H09, H21, D72, D85;
- optional zone configurations.
Full Q6/Q19 retain their separate candidates, including generic-smallest using
that same Fine/canonical/smallest pipeline. All 29 registered CASES (27 retail-
derived and two full queries) offer default and transfer; this is not canonical
Q1-Q22 coverage. Transfer does not change input projections or cached schemas.
All hosts are typed Vecs loaded from the same projections. This is a small
candidate set, not an exhaustive planner search. The metadata records the
best measured configuration for each query/scale from this set; candidates
are not assumed faster than default. Initialization/index building is charged
to every run; no configuration gets uncharged persistent prebuilt indexes.

Explicit string predicates
H05, H07-block, D27, and H08 bind string columns to query names and state their
restrictions with explicit == predicates. H07-block keeps those names local to
their respective branches. SQL, projected answers, and existing date conditions
are unchanged; the original literal-bearing forms remain historical measurements.
This is an authored representation choice, not a compiler reinterpretation of
literal binding. Literal-bearing Rename retains its filtered/projected occurrence;
recognized predicates instead permit Point/Select and const-read planning.
Retention, keyset selection, and additional scan filters still depend on consumers.
Compare emitted plans and measured work rather than assuming the two forms have
the same storage or that every predicate adds a join filter.

H05 order advisory
cargo xtask bench --tpch --sf 1 --runs 5 --query retail_h05 --config advised
selects checked order(Lineitem, Orders, Customer, Supplier, Nation, Region).
The Supplier/customer-nation cycle is checked before Nation/Region expansion;
the written Lineitem/Orders prerequisites of the date guard remain intact.
Order advice leaves the authored CQ body and SQL unchanged. It is opt-in:
default remains the control, and --index-comparison still selects its existing
same-plan provider families. No filter-policy, provider, or compiler change is
part of this advisory.

Controlled hash/RadixSpline comparison
cargo xtask bench --tpch --sf 1 --runs 5 --index-comparison
selects default, radix, radix_retained for every catalog entry, including every
stage of handwritten multistage kernels. Where built_hash/built_radix are
authored, it also selects that matched pair (currently 17 kernels, 121 rows
across all 29 kernels). A partially advertised built pair is an error.
It is mutually exclusive with --config and --reduction-comparison. Radix retains
the default logical/Physical plan and adds only cq_rewrites::radix_runs;
radix_retained additionally requests checked lookup-witness reuse. The command
does not select the LE planner.

The provider advice affects eligible explicitly built singleton integral payload
indexes. It does not automatically change host fallback indexes, membership-only
structures, or composite keys. A named radix configuration can therefore be a
no-op. Counters and plan captures must be consulted before attributing a timing
difference to the provider. Retention is also conditional on an eligible
semijoin/probe pair; its configuration name does not prove a changed schedule.

The common retail-kernel and Q6/Q19 configuration wrappers additionally offer
built_hash and built_radix. Both apply checked build_host_reads first, so the
materialization policy is held fixed; only built_radix applies radix_runs.
The full --index-comparison includes these pairs automatically. Targeted runs
can still use --query retail_h09 --config built_hash and then --query
retail_h09 --config built_radix. Compare the built_* rows to one another, not
against default when attributing a difference to the provider. Unsupported
composite payload keys remain hashed in both. The handwritten grouped-only
wrappers do not advertise these additional configurations. Report real provider
switches separately from advisory no-ops, using emitted builds and counters.

H09 order selection on the Mac branch
The opaque Part substring guard remains first. Local SF1 DuckDB cardinalities
were collected for all 16 distinct prefixes among 18 connected Part-first
left-deep orders. The minimum sum of prefix rows is Part -> PartSupp -> Supplier
-> Nation -> Lineitem -> Orders (777,440 rows), but it requires a composite
Lineitem index. A measured alternative, Part -> Lineitem -> PartSupp -> Orders
-> Supplier -> Nation (1,607,684 prefix rows), is faster in the measured comparison
and uses a single-key Lineitem index. The authored body now uses that alternative;
SQL, predicates, and output semantics are unchanged. This is the best of the two
measured index-shape candidates, not a claim of globally optimal execution.
The original Part -> Orders prefix had 15,996,000,000 SF1 candidate pairs.
Original timings, exact cardinality SQL, both candidates, and the materialized
provider comparison are retained under experiments/mac/index-bench/results/
tpch-m3max-2026-10-24 (relative to the repository root).

Timing and memory
Both the synthetic bench and TPC-H-derived path automatically build/run release
code. Each measured configuration runs in a fresh worker process, loads once,
checks one warm result, and reports the median of five executions by default.
An odd run count of at least three may be requested. Each timed execution
constructs a fresh query, builds required indexes, runs and fully materializes
its typed output. Load time, string formatting, answer-set normalization,
comparison, file I/O and result destruction are outside the query timer.
The shared testkit/bench-check helper checks the first measured sample of each
binary/configuration fully against the retained DuckDB reference. Later samples
check exact logical answer counts and up to 1,000 seeded actual tuples for
reference membership (all if smaller). Warmup exactness does not replace the
first measured full check. Reference indexing is outside the sample loop;
validation mode, seed, sample count and seconds are retained in worker evidence.
Tests, zero-run correctness gates and independent counter checks stay full.

DuckDB uses separately preloaded in-memory tables from the identical Parquet
projections. Its load is measured separately. Both threads=1 and the engine's
observed default thread count are reported. Each mode performs its correctness
execution and one additional explicit warm execution before N measured runs.
DuckDB CLI timing includes preparation/planning/optimization, execution, CSV
serialization, transfer and parsing. The separately reported execute-only mode
prepares once outside sampling. CLI startup and table preload are excluded.
MiniLinq produces a Vec of typed Rust tuples and excludes textual conversion
from its query timer. These are end-to-end execution boundaries, not identical
output layouts or isolated operator benchmarks.

The getrusage peak_rss_kib reading is the worker process peak RSS. It includes
loading, oracle/answer witnesses, warmup, all samples, and canonical comparison;
it is not incremental query-only memory. Non-Unix platforms report NA.
MiniLinq timing uses a release executable compiled with cq-storage instrumentation disabled. Counters come from a separately compiled release executable and two untimed executions, each checked exactly against DuckDB. DuckDB is also timed without operation counters.
Counters are the existing cq-storage counters: hashes, index builds, lookups,
cursor steps, row enumeration and distinct insertions. Extension aggregate
folding and uninstrumented host operations are not covered by those counters.
RadixRun's internal arrays and direct range traversal are not completely covered
by legacy retained-byte/row counters. Those columns are not an apples-to-apples
heap-footprint or memory-traffic comparison with HashIndex.
Q6/Q19 explicitly materialize computed rows before aggregate! because the current
aggregate extension expects borrowed measure columns. Both phases and that
intermediate allocation are timed.

Compilation
A generated isolated binary crate per query contains its configurations plus
the shared worker. Cargo release --timings supplies that binary unit's duration,
excluding separate dependency units. Proc macros (the compiler) build at
opt-level 3. Generated sources are stable, so an unchanged worker is reused and
reports compile_unit_ms NA; edit any input to obtain a fresh compile time.
This duration includes macro expansion, Rust checking, optimization/codegen and
linking; it is not an isolated measurement of proc-macro CPU time. Dependency
versions are seeded from the repository lock and the release build is locked.
The HTML report is retained under target/bench/compile. All queries compile
before timing begins; no compiler process is intentionally run during query
measurement. Times are descriptive and are never asserted or used as a gate.

Output
The complete TSV has one row per query/configuration/scale. Companion JSON
records raw sorted samples, SQL, export schemas, configurations, compile reports,
engine/compiler versions and methodology. A .partial TSV is used during a run;
the final TSV is replaced only after the entire requested suite passes.

Resource evidence uses getrusage(RUSAGE_SELF), including all worker threads.
The TSV appends query_minor_faults, query_major_faults and query_peak_rss_kib:
these belong to the same execution as query_median_ms, not independent medians.
Minor/major faults are ru_minflt/ru_majflt deltas immediately around query::run;
the getrusage calls themselves are outside the wall timer. Input loading,
canonicalization, exact comparison and result drop are outside this boundary.
query_peak_rss_kib is ru_maxrss sampled immediately after that execution, a
process-lifetime high-water mark, NOT query-only allocation or an RSS delta.
It includes earlier load/warmup/correctness work. peak_rss_kib retains its
whole-worker meaning, sampled after all measured runs. Darwin bytes are
converted to KiB; unsupported non-Unix hosts emit null in JSON / NA in TSV.
On fork/exec hosts this high water can also include the child's inherited
pre-exec address space; it must not be interpreted as incremental query RSS.
Timed worker JSON has samples_minor_faults, samples_major_faults and
samples_peak_rss_kib aligned with sorted samples_ms. warm_minor_faults,
warm_major_faults and warm_peak_rss_kib capture the first untimed query
separately, so allocator first-touch is not hidden by the warmup. No noisy
resource observations are included in deterministic counting-run comparisons.
For a focused SF1 evidence run:
  cargo xtask bench --tpch --sf 1 --runs 3 --query tpch_q06 --config default
Other catalog names are listed in src/tpch.rs.

Join-filter configurations
H03, D85, H07 and H09 declare join-filter-advised explicitly in their source.
H03, D85 and H09 use the default plan and positional selection, then retype the recorded
join-filter entries to cq_join_filters::BloomFilter<16384> (128 KiB of bits).
Default selection records only exact AdaptiveKeySet structures. The additional
join-filter-always-true configuration checks the covering probes against DuckDB
with a filter that rejects nothing. H07's default reduction retains its scans,
so it has no eligible join-filter entries. Its three join-filter configurations
explicitly use plan(no_reduce). The join-filter-exact configuration uses the
same plan as join-filter-advised, isolating filter choice; for the other three
kernels join-filter-exact is identical to default. Compare H07's default with
its unreduced configurations as a whole-plan comparison, never as evidence of
filter-only speedup. Retyping preserves clauses and the covering exact probes.
All filter construction costs are inside each measured execution. The feature
uses the public Retention accounting companion for its owned bit allocation.

Operator profiling
------------------
cargo xtask profile --tpch --sf 0.1|1 [--query NAME] [--config NAME] [--output DIR]
selects default when no configuration is supplied. Artifacts, raw DuckDB JSON,
per-run counts/timings and validation witnesses go to --output DIR, or
/data/codex/opprofile-evidence/ when omitted. Use a writable local directory on
macOS. The requested scale is recorded in every file; running a second scale
replaces the named summary files. Raw runs keep the scale.

cq-storage/counters selects the measured pull expression through profile_select!;
the unselected expression disappears during macro expansion. The default pull
pipeline lowers Structures to Sequence, checks host-only grading, then uses
cq-sequence-pull::translate or cq-sequence-pull::translate_profile. Physical and
Structures representations and the selected algorithms are unchanged.

Each Physical result has a record even when no consumer demands it. Positional
projections folded into immutable selections are aliases: their rows and inclusive
span come from their source. A source accessed through a fused positional predicate
counts tested occurrences, after metadata pruning, and shares that predicate's span.
Native ordered host reads and fused intersection members share their combined
consumer's span; the profile does not invent exclusive timing for fused work.
Input counts describe demanded streamed rows; indexed sides have separate build
records. Index/keyset/filter insertion counts include duplicates; native keysets
also report their distinct retained cardinality. ANSWER is the generated relational
answer; QUERY additionally covers extension aggregation and typed result collection.

Iterators count rows locally, publishing at exhaustion/drop. Predicates increment
Cells. Stream timing uses Instant on first demand and exhaustion/drop, without
read-ahead, materialization, per-row clocks, or changing short-circuit behavior.
These cumulative pipeline spans include upstream and downstream work between
requests; they are inclusive, overlap, and must not be added. Synchronous builds
use one clock pair. Deferred HashIndex/KeySet initialization is timed when consumed;
a never-demanded build has zero calls/time. QUERY is the independent top-level
execution scope; its wall time includes all builds and final collection, excluding
fixture loading, canonicalization/serialization, answer checking and answer drop.
DuckDB's JSON operator timings are displayed as provided; they are not the same
quantity as our inclusive pipeline spans.

The runner warms both workers, fully checks each binary/configuration's first
measured sample, then checks exact counts and up to 1,000 seeded actual tuples
against the reference in later samples using testkit/bench-check. It reports the
median of eleven executions and the measured overhead against a separate release
worker without counters. It does not subtract estimated overhead or scale the
operator times to make them agree with an uninstrumented measurement. Dated
results retain the full-per-sample policy used when they were recorded.
The timing worker enables cq-storage/operator-timing, independently of counters,
for operator clocks with the normal aHash algorithm and row/primitive counters
disabled. A separate counters-only worker supplies operator rows and primitive
counters; summed operator insertion counts must equal independent
rows_copied/distinct_insertions (excluding runtime candidate-enumeration dedup
attempts, recorded separately). The timing worker must reproduce exactly the same
operator graph/labels and SQL answers. Its report combines those independently
counted rows with measured clock spans. No per-row counting runs inside the timed
phase; this avoids presenting counter overhead as operator execution cost.
The legacy counters-only worker retains its historical DefaultHasher measurements.
The timing worker uses the same HashState as ordinary execution; only the
separate counting worker fixes seeds. Reported overhead includes operator clocks
and bookkeeping. Primitive counters are never subtracted from timings.
Shared-machine noise and random hash seeds can affect this ratio. Timing wrapper types can also perturb compiler code layout; a negative delta is not a query optimization result. No few-percent overhead claim follows from matching
row counts or the top-level clock; consult the validation files for measured ratios.

On Linux, CQ_PROFILE_CPU=N pins both worker variants and the validation worker
to CPU N via taskset; compilation remains unpinned. The selected CPU is recorded
in the validation JSON. This reduces scheduling variation without changing plans.
